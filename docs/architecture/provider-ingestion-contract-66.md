# Provider ingestion contract 66

**Status:** repository candidate only  
**Hosted authority:** none  
**Production authority:** none

## Purpose

Contract 66 introduces the minimum safe custody boundary for external football fixture and result providers. It does not make any provider authoritative for application fixtures or results and does not write decoded data into competition-owned tables.

## Providers

The server-only poller supports three explicit provider contracts:

- SportMonks;
- API-Football;
- football-data.org.

Each provider has a strict decoder. Missing required objects, identifiers, dates, participants or invalid score values fail closed with a path-specific `ProviderDecodeError`. Provider payloads are never passed through as application domain data.

## Archive-before-decode rule

The Edge Function must:

1. authenticate the caller as the Supabase service role;
2. fetch only from the selected provider's fixed HTTPS origin;
3. read the exact response body as text;
4. archive that text and response metadata through `archive_provider_response`;
5. only after the archive succeeds, parse JSON and run the provider decoder;
6. append a success or failure attempt through `record_provider_response_processing`.

If archival fails, decoding must not run. A provider HTTP error is still archived and receives a failed processing record.

## Database boundary

`provider_raw_responses` is a private, RLS-enabled, forced-RLS, append-only custody table. Its `raw_body` is the exact text returned by the provider and its SHA-256 digest is generated by PostgreSQL.

`provider_response_processing` is a separate private append-only table. Decoder retries create new rows; they never mutate the raw response or an earlier attempt.

Neither table has a browser policy or browser grant. Both RPCs:

- are `security definer` with an empty `search_path`;
- require the request JWT role to be `service_role`;
- revoke execution from `public`, `anon` and `authenticated`;
- grant execution only to `service_role`.

## Secrets

Provider credentials belong only in development Supabase Edge Function Secrets:

- `SPORTMONKS_API_TOKEN`;
- `API_FOOTBALL_API_KEY`;
- `FOOTBALL_DATA_API_KEY`.

The function also relies on Supabase-managed `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. No credential belongs in the repository, Netlify or browser environment variables.

## Non-authority and rollout boundary

Contract 66 does not:

- deploy the migration or Edge Function;
- set or rotate a secret;
- call a provider;
- map provider teams, competitions or fixtures to application records;
- update a match, result, score, lock or standings table;
- change Netlify or production.

A first poll may occur only on hosted development after the migration and function are separately approved and deployed, all three secrets are present, an unauthorised request is proved rejected, and the selected endpoint and expected response shape are reviewed. Production remains prohibited.

## Evidence required before merge

- clean zero-to-contract-66 rebuild;
- database lint;
- complete pgTAP suite;
- migration and RPC signature parity;
- strict decoder unit tests;
- source guard proving archive precedes parse/decode;
- Edge Function bundle;
- unauthorised request rejection;
- no hosted write, provider call, Netlify change or production action.
