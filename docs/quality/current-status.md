## Provider-ingestion authority boundary

Contract 96 is custody, not promotion:

- the Edge Function accepts only named, fixed providers and bounded relative paths;
- the caller key is checked before any provider I/O;
- exact raw response text is archived before parse or strict decode;
- processing attempts are append-only evidence;
- browser roles receive no relation or RPC access;
- safe response headers are allowlisted and response size is bounded;
- credential-shaped query parameters are rejected;
- no provider path may write official fixtures, results, lock state, points, totals, ranks or standings.

No provider credential or provider request is part of contract 96 delivery.

**Retention is permitted (owner confirmation, 5 August 2026).** All three providers allow their responses to be stored. This is recorded because it was the blocking question rather than a formality: the custody design archives exact raw response text and keeps it, so a licence permitting the call but not the retention would have made the control itself the breach — and it would have been discovered only after the data was stored. Coverage, timezone and exceptional-state mappings are still open; those are measured, not asserted, by `scripts/ops/provider-bakeoff.ts`.

**The identity map exists at contract 112, and is applied to development.** `public.provider_entity_map` relates a provider's season, round and team identifiers to this platform's rows, always within one competition season. It is the map alone: it resolves, and it reports which identifiers in a payload are still unmapped and how many fixtures each one blocks. It imports nothing.

The scoping is a composite foreign key rather than a convention — `(tournament_id, team_id)` — so the database itself refuses to map a provider identifier onto a club in a different competition season. That mistake is otherwise entirely silent: the fixtures produced would be plausible and wrong, and what anyone would see is a league table that is subtly untrue rather than an error.

**Why the map and nothing else.** Building it found the reason. `src/domain/season/fixtureReassignment.ts` resolves a moved kickoff by ROUND WINDOW, and `competition_rounds` had no window columns. Inventing one inside an ingestion migration would decide a lock-adjacent rule as a side effect of plumbing, so it got its own contract.

**The round play window is contract 113, applied to development.** Each round carries the inclusive span it is played over, derived from its own fixtures, with a trigger keeping windows disjoint within a competition season. The bounds are inclusive at both ends to match the domain module's containment test, so windows that merely *touch* are refused — an instant on a shared boundary would fall in both rounds, which is precisely the ambiguity being excluded. It is stored rather than computed at resolve time because the derivation reads fixtures and reassignment moves one: computing at the moment of the question would make the answer depend on it.

**The decision that followed, and what it costs contract 113.** Contract 113 was built to answer "which round does this kickoff fall in", because [ADR 0020](../adr/0020-football-prediction-hub-product-model.md) §79 reassigns a rescheduled fixture to that round and never defines *falls in*. The owner amendment of 5 August 2026 **reverses that section**: a rescheduled fixture is not reassigned at all. It stays in the matchweek it was scheduled in, its prediction stays editable until its own kickoff, and a single moved match never creates a round. **The round is a label, not a position:** the fixture still scores into its original matchweek, but wherever fixtures are listed by date it appears at its actual kickoff in true chronological order, carrying its original matchweek as its label. Grouping strictly by round is the comfortable misreading, and it would put a November match under a September heading above matches played weeks earlier.

That is a simpler rule and mostly existing machinery — ADR 0020 already names the per-match guard as the integrity floor, and Stage C1's lock enforcement already compares against each fixture's current kickoff, so the amendment promotes that guard rather than introducing anything. It also removes a class of question outright: no boundary between matchweeks has to be chosen, and points cannot move between matchweeks after the fact.

**It also removes contract 113's stated consumer, and that is recorded rather than glossed.** The play window is still a true fact — it is when a round is played — but reassignment no longer asks the question it was built to answer. Either it finds a justified use or it is recorded as unused capability; what it must not do is keep a migration header claiming a purpose the amendment removed.

**What is still missing between a provider response and a fixture.** Nothing writes `season_fixtures` — the Stage C1 foundation says so in terms, deferring "the ingestion and administrative reassignment workflow" to a later contract. The shape it takes is decided **by change class**, in [ADR 0023 § Administration and provider changes](../adr/0023-hub-information-architecture.md#administration-and-provider-changes): an existing correctly mapped fixture's kickoff may be revised automatically (`INGEST-001`), while a newly discovered fixture, a removal, a cancellation, an abandonment or a material identity or round change each require administrative approval (`INGEST-002`, `INGEST-003`). Ambiguity fails closed (`INGEST-004`), and provider data never becomes official result truth automatically (`INGEST-006`) — official scoring and progression stay governed by the existing fail-closed result rules.

This paragraph previously restated ADR 0020's earlier wording — "fixture changes import automatically and notify an administrator for review" — as though it were one rule for every change class. It is not, and reading it that way would authorise a provider to create and delete this platform's fixtures. The boundary is stated once, in the decision, and linked from here rather than copied.

**Deployment status, corrected 5 August 2026.** The Edge Function is no longer undeployed: `provider-poll` version 1 is `ACTIVE` on development (`iouzoutneyjpugbbtdem`) with `verify_jwt: false`, deployed on owner authorisation and recorded with its bundle hash in [`docs/ops/ops-provider-poll-deployment.md`](../ops/ops-provider-poll-deployment.md). Deploying it establishes only that it exists and that its bundle parses. **No provider has been contacted, no credential has been spent, no raw response has been archived, and the named caller key has not been observed to resolve** — the probe that would confirm the last of those cannot run from the agent environment, and the record above says why and gives the command. The custody boundary above is unchanged by the deployment: it is the same code, now reachable.

**The database can now call it — contract 115, applied to development on 6 August 2026 by fast-lane run 31083613351.** The question this answers is the owner's: should Supabase not be calling the provider API directly? It should, and two of the three layers were already there. The Edge Function runs on Supabase and holds the three provider credentials as Edge Function secrets, so the outbound call has always been meant to leave from Supabase's servers rather than a browser. `pg_cron` 1.6.4 has driven recurring jobs since contract 82 and currently runs five of them. What was missing was measured rather than assumed: `pg_net` showed `installed_version: null` on development, so **PostgreSQL could make no outbound HTTP request at all**, and every one of those five jobs calls a plain SQL function. Contract 114 installs the extension and wires both ends — `pg_cron` → `public.dispatch_due_provider_polls()` → `net.http_post` → the Edge Function → the provider → contract 96's archive and processing evidence.

Two things it deliberately does not do, for the same reason contract 112 stopped where it did. It **imports no fixture**: turning a decoded fixture into a `season_fixtures` row needs the identity map to have rows, and it has none, so writing the import now would mean inventing the mapping as a side effect. And it **records no poll target**: there is no authority anywhere in this repository for a provider's URL shape, and a migration that guessed path templates would be publishing three guesses as fact. What it stores instead is a target *table* whose CHECK restates the Edge Function's own path rules, so a target the Edge Function would reject with a 400 cannot be stored at all.

**The caller key resolves — measured, after a fix the probe itself found.** The Edge Function authorised callers
against a secret key named `provider-poll`, matching its own slug. That key cannot exist: Supabase rejects a hyphen in
a secret key name. Two probes through `net.http_post` with a deliberately wrong `apikey` returned HTTP 500
`function_not_configured`, detail `Missing named Supabase secret key: provider-poll`. `CALLER_KEY_NAME` is now
`provider_poll`, the function was redeployed from the committed sources as **version 3** (`ACTIVE`, `verify_jwt:
false`, `ezbr_sha256 2b45e969…`), and the identical probe returned **`401 unauthorized`**.

That change of answer is the evidence: the named key now resolves inside the function and a wrong key is refused. The
function slug is unchanged and still `provider-poll`; only the key name differs, by one character, which is why both
the constant and its guard test now say so in a comment. **No provider was contacted by any of the three probes** —
the function answers on its own configuration and its caller's key before it reads the request body. No provider
credential has been exercised and nothing has been archived.

**The first live poll ran on 5 August 2026, and it worked.** Owner-authorised for one bounded target before the
first credential spend: `football-data` · `/competitions/PL/matches` · Premier League 2026/27 · hourly. The dispatcher

all `SCHEDULED`. Custody held in the order it was designed to: 365,300 bytes archived verbatim *before* decoding, then

**The synthetic seed and real data now coexist, and the boundary is enforced rather than remembered.**
`scripts/seed-dev/seed-league-seasons.ts` stays committed because CI and Browser E2E need a deterministic calendar
that never calls a provider. It was first described here as able to overwrite real football; **that was an

**The target was then disabled, on owner direction, after exactly one API call.** Hourly polling during development spends quota on a fixture list nobody consumes. A weekly cadence is not expressible — the CHECK caps at 1440 minutes, because a target polled less often than daily is a manual refresh rather than a poll — so the target is disabled rather than given a schedule it does not keep. Verified: `due: 0`, `dispatched: 0`, one dispatch row in total. The row is kept as the reference for a correct target, and re-enabling is one statement.

**What an operator must supply before it does anything**, stated here because the job is otherwise silently inert: two `vault` secrets — `provider_poll_function_url` (https only; an `http://` value raises rather than returning null, because sending the caller key in clear text is a misconfiguration to fix rather than an absence to tolerate) and `provider_poll_caller_key`, the project secret key named `provider-poll` that the Edge Function compares against in constant time — and at least one row in `public.provider_poll_targets`. Until then the job returns `configured: false` and `due: 0` every five minutes, which is an ordinary answer rather than an error: a job that failed loudly until somebody finished setting it up would be noise nobody reads by the time it means something.

**Two retention items are recorded as accepted and unbuilt rather than claimed.** `MIG-UI-18` is a leaderboard neighbourhood read: rank travels with field size everywhere and the caller's own row is always reachable, but who is immediately above them is not derivable from a cursor that pages downward from rank 1, and forty round trips to answer one sentence is not an implementation. `MIG-UI-19` is a season share card, which is not blocked on a contract at all — every fact it needs is readable — but on a design decision about what a league-season card shows, since the existing renderer draws a tournament bracket from country flags and a predicted champion.

**ADR 0026's two deployments exist as builds, as of 11 August 2026.** `SITE-002` was accepted and unbuilt: one commit was meant to produce the weekly Prediction Hub and the Euro 2028 Predictor as separate sites on separate domains, and nothing in the repository could tell them apart. Three static files hard-coded `https://euro28predictor.com` — `index.html`'s canonical and Open Graph tags, `public/sitemap.xml` and `public/robots.txt` — so a Hub build would have pointed every crawler and every unfurled share link at the Euro site.

`VITE_SITE_VARIANT` now selects the product at build time and everything that differs between the two is one typed `SiteConfiguration` (`src/app/site/`): brand, navigation order and wording, which game is primary and which are Bonus Games, addressing, and whether the Euro tournament's routes are served at all. It **fails closed towards the Hub** — unset, misspelled or unknown builds the weekly platform, never a tournament nobody published — and `validate-netlify-environment.mjs` refuses a build whose variant is neither value, because a typo would otherwise deploy the Euro site as the Hub in silence.

Three properties are worth stating exactly, because each is a thing the seam is for:

- **An unconfigured origin emits nothing.** No canonical tag, no `og:url`, no `og:image`, no sitemap and no `Sitemap:` line — never a fallback, because the only default available is the other site's domain. The Hub's permanent domain is not purchased (`SITE-003`, blocked on the brand decision), so that is its expected state today rather than a gap.
- **`EURO-001` is advanced on its public half and deliberately not on its route half.** The Hub build's head, sitemap and `robots.txt` name no tournament and no tournament domain. `TournamentJourney` also gained a deployment gate that refuses the tournament's player routes before it reads anything — but **both deployments still set `servesEuroTournament` true**, so the weekly platform continues to serve them.

  That is a reversal within the session and it is recorded rather than quietly dropped. The gate was set for the Hub, and the browser suite caught what it actually cost: `/tournament/profile`, `/league/:id` and `/h2h/:rivalId` are covered by specs the repository keeps as `euro-2028-baseline` return evidence, and there is no Euro-variant browser configuration for them to run under — so withdrawing the routes deleted that evidence instead of moving it. Withholding `/admin/results` was worse and simply wrong: there is no separate administration deployment, so it removed the only Results Centre there is, and a hidden tournament could no longer be prepared to the point of being publishable. That exemption is restored and is now explicit in both gates.

  **What remains is an owner decision plus a browser-suite move, not a control to design.** The refusal is built and proven against an explicitly-configured non-tournament site, so turning it on is one configured value with evidence behind it. The publication gate is untouched and still owns whether a served tournament may be seen.
- **The Euro site has its own front door, keyed on contract 143.** `EuroLandingPage` renders the tournament led, with the three weekly games beneath it under Bonus Games — present rather than trimmed away, and with the same names and descriptions they carry on the Hub. Before the publication read returns, and for ever if it fails, it renders the closed presentation: an outage produces a visitor who plays the weekly games, never one told to register for a tournament nobody opened. Account creation appears in exactly the two states that have it. There is no draw, no team, no fixture and no countdown — the tournament's own surfaces are parked until January 2028.

**What is NOT claimed.** No second Netlify site exists and no domain is bound; creating one is an operations task outside a frontend session's authority. `SITE-004` and `SITE-006` remain unimplemented as deployments.

**Contracts 169 to 171 are not consumed by this branch, and the reason changed under it during the session.** When the work was done, Development was hosted at 168 and the three contracts had reached no hosted environment, so the fields were not expressible from a browser at all: `database.types.ts` is generated from Development, and since `TYPE-001` closed there is no untyped client to reach for. That is no longer the position — Development and Production both reached **171** the same day, through PR #697 and the Production 158-to-171 rollout. **What still blocks consumption is one step, and it is a mechanical one:** the generated types in this branch were produced at 168 (`database.types.meta.json`), so contract 169's `table_source` and contract 171's `members_returned`/`members_truncated` still do not exist in the typed client here. Regenerating through `regenerate-database-types.yml` against Development at 171 is the next step, and the surfaces that would consume them are named: the season Championship table's span label (169) and the league prediction lists' "showing 200 of 205" (171). No frontend rule or decision is waiting on anything.

**Contract 158's rotate control is no longer unreachable.** `rotate_league_invite_code` shipped for `SEC-001` and nothing called it, so an owner whose invite code had got out could only delete the league and start again. The season Leagues surface now offers it to an owner, behind a confirmation that states the consequence rather than asking "are you sure?": it names the code about to stop working, says anyone already sent it will not be able to join, that it cannot be put back, and that members already in are unaffected. It is owner-only presentation over an owner-only command; a refusal reaching a stale page is shown, mapped through `userFacingError` so no RPC detail reaches a player.

**One accessibility and resilience defect closed.** Every auth form gates submit on holding a Turnstile token, and the only failure signal was `onToken(null)` — indistinguishable from "not solved yet". The script is third-party and cross-origin, so a content blocker, a corporate proxy or an offline device stopped it arriving routinely; when it did, a visitor got a sign-up page with a permanently disabled button, no widget and no message, and could neither create an account nor find out why. `TurnstileField` now explains the failure, offers a retry that mounts a fresh challenge, and offers a support address where one is configured. It weakens nothing and adds no bypass: a failure still yields no token, submit is still refused, and Supabase runs siteverify server-side in any case.

**No hosted claim is made here.** These are repository facts. The signed-in hosted acceptance is `UI-F19` and remains outstanding.
